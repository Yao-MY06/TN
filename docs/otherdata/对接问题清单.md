## 1. 接口约定类

### Q1【问组长】`frame_id` 起始值

- **问题**：从 0 还是从 1 开始？
- **我们的暂定**：**从 0**（OpenCV `CAP_PROP_POS_FRAMES`、FFmpeg、绝大多数 CV 数据集与标注工具惯例）
- **不一致的后果**：三家事件时间轴整体错 1 帧。25fps 下 40ms，而事件去重窗是 ±0.08s（±2 帧），
  **差 1 帧恰好落在窗口边界**，会造成偶发漏融合——最难查的那类 bug。

### Q2【问组长】`side` 的 A/B 语义 ⚠️ 最优先

- **问题**：A/B 代表**球台物理左右半台**，还是**发球方/接发方**？
- **我们的暂定**：**A = 画面/球台左侧物理半台**，与主客无关；主客关系由状态机结合发球轮次换算。
- **为什么最优先**：两种理解在数据上**长得完全一样**（都是 `"A"`/`"B"`）。
  若各家不一致，程序**不会报错**，只会在融合时把两套语义混在一起，**静默判错分**。
- **建议**：定完请向三条分支各广播一次。

### Q3【问组长】`timestamp_s` 的基准

- **问题**：是否统一为「视频时间 = `frame_id / 视频实际fps`」？三家是否跑**同一份解码视频**？
- **我们的暂定**：`frame_id / cv2.CAP_PROP_FPS`，**不假定 25fps**（数据集文档也提醒过
  TT3D 的 200Hz 是真值采样率、不代表视频帧率）。
- **补充问题**：遇到**可变帧率（VFR）视频**怎么办？是否改用逐帧 PTS（`CAP_PROP_POS_MSEC`）？
- **不一致的后果**：组长 §4-1 要求"用时间戳不用固定帧数"，但若时间戳基准不统一，
  所有超时/冷却/去重/消抖判据全部失效。

### Q4【问组长】§2 与 §7.1 的命名冲突

- **问题**：组长文档里有两套互不兼容的字段命名，以哪套为准？

  | | §2（简化示例） | §7.1（详细设计） |
  |:---|:---|:---|
  | 时间 | `timestamp` | `timestamp_s` |
  | 球位置 | `ball_xy`（扁平） | `ball.center_px`（嵌套） |
  | 可见性 | `ball_visible` | `ball.visible` |
  | 事件分数 | `bounce_score` | `event_scores.bounce` |

- **我们的暂定**：**按 §7.1**（§7 开头写"细化第 2 节的简化示例，建议统一采用本节字段命名"）
- **为什么要问**：如果 TTNet 按 §2 实现、我们按 §7.1 实现，两边字段**直接对不上**，联调失败。
  这是**组长文档自身的内部矛盾**，只有组长能定。

### Q5【问组长】完整事件类型枚举

- **问题**：`RefereeEvent.type` 的完整取值与英文命名？
- **现状**：§7.4 只给了 `BOUNCE` 示例，注释是"落台、击球、擦网**等**"（开放式列举）。
- **我们的暂定**：4 类物理事件 —— `BOUNCE` / `RACKET_HIT` / `NET_TOUCH` / `OUT`
- **需要明确**：
  - "击球"用 `RACKET_HIT` 还是 `HIT`？"擦网"用 `NET_TOUCH` 还是 `NET`？
  - **"出界"是独立事件，还是由状态机从落点推导？**
  - **"擦网重发（LET）"是事件还是状态机输出？**（我们倾向后者：LET 是判罚结果，不是物理事件）
  - **"回合结束""得分方"我们不放进事件枚举**（它们是状态机输出），这样理解对吗？

### Q6【问组长】事件级 `confidence` 怎么算

- **问题**：§7.4 要求 `event` 带 `confidence`，但 §7.2 说"不同模型原始分数不能直接比较"、
  §4-3 说"置信度不能直接取最大值"。**两条约束禁止了最自然的做法，却没给替代算法。**
- **我们的理解**（请确认）：要区分两个层级 ——

  | | 观测级 | 事件级 |
  |:---|:---|:---|
  | 字段 | `observation.ball.confidence` | `event.confidence` |
  | 含义 | **单个模型**的检测分数 | **事件层**对"确实发生了一次落台"的评估 |
  | §7.2 是否适用 | 适用（YOLO = 检测置信度） | **不适用** |

  依据：§7.4 示例是 `{"confidence": 0.90, "sources": ["ttnet","tracknet"]}` ——
  **两个来源、一个置信度**，说明它是融合后的单一数值，不是任何模型的原始分数。
- **我们的建议**：事件级 confidence 由事件层**自评**（几何一致性 + 多源一致性），
  **不引用任何模型的原始分数**。三模型并行时的融合公式请组长定。

### Q7【问组长】事件去重时间窗

- **问题**：§4-3 要求"同一次落台只能产生一个事件"，但没给时间窗大小。
- **我们的暂定**：**±0.08s**（25fps 下约 ±2 帧）
- **风险**：窗口过小 → 同一次落台算两次（重复加分）；窗口过大 → 连续两次真实击球被合并（漏判）。
  乒乓球高速对拉时两次击球间隔可低至约 0.2s。

### Q8【问组长】坐标与分辨率基准

- **问题**：三家是否跑**同一份视频、同一分辨率**？
- **我们的理解**（请确认）：**不应约定统一分辨率，接口必须自适应**。依据是《数据集》文档：
  公开集只用于训练检测（TT ball）与验证轨迹落点（TT3D），端到端判分要靠**自录完整回合**——
  数据源本来就是多样的。
- **我们的实现**：`image_size` 填每帧原图尺寸（§7.1）；球台标定按分辨率自动缩放；
  `timestamp_s` 由视频实际帧率换算。像素阈值随分辨率等比缩放（有单测）。

## 2. 状态机类（当前唯一实质阻塞）

### Q9【问组长】判罚细则由谁牵头统一 ⚠️

- **问题**：组长 §3 只给了**状态序列**（等待发球 → 发球进行中 → 对打中 → 回合结束候选 →
  确认得分，旁路"无法判断，等待人工确认"），且措辞是"**可以先设置**"。
  以下**判罚细则组长文档未规定**：
  - 发球三段校验的具体判定（己方半台落台 → 越网 → 对方半台落台）
  - 擦网重发（LET）的判定与比分处理
  - 回合终了的消抖时长
  - 双跳违例判定
- **为什么必须统一**：这是**三分支最容易各写一套**的地方，直接违背组长
  "不要三套互不相通的计分规则"的核心意图。
- **我们的建议**：**由我们起草一版细则，报组长审**（省组长时间，也能让另两条分支直接评审）。
- **在细则落地前**：我们只实现状态机骨架，阈值全部参数化，不空等。

### Q10【问组长】`MANUAL_REVIEW` 的触发、退出与接口

- **问题**：§3 提到"无法判断，等待人工确认"，但未定义：
  - **什么条件进入**（多模型冲突？置信度低于阈值？事件严重矛盾？）
  - **如何退出**（人工确认后如何恢复比赛状态、比分如何处理）
  - **接口形式**（§1 架构图里写了"语音纠错/实体按键"，具体是什么协议？）
- **为什么必须问**：不定义则状态机无法闭环。

### Q11【问组长】状态机的输入接口

- **问题**：状态机是否**只吃 `RefereeEvent`**？
- **我们的假设**：是（组长 §7 末尾："适配器输出 Observation → 追踪、事件提取与融合 →
  输出 Event → 计分状态机"）。
- **补充**：是否需要额外的"回合开始/结束"信号，还是全部由事件 + 超时推导？

## 3. 融合与评测类

### Q12【问组长】当前阶段：分别对比 还是 同时融合 ⚠️ 架构级

- **问题**：组长文档里有两处表述，对应**两种不同架构**：
  - §4-3："**如果三个模型同时运行**，要先融合、去重，再送入状态机"
  - §6："用同一段视频**分别测试**三个模型，可以直接比较最终判分准确率"
- **为什么重要**：若是"分别跑"，当前**不需要**融合层；若是"同时运行"，需要实现
  跨模型事件融合 + 冲突检测。
- **我们的判断**：§6 说的是**当前部署建议**（分别跑做横向对比），§4-3 是为将来同时运行预留。
  **请确认**，这决定我们要不要现在做融合层。

### Q13【问组长】横向对比的评测协议

- **问题**：三家的"判分准确率"如何统一口径？
- **需要统一的东西**：
  - 评测视频（同一份？哪几份？）
  - 真值标注（落台/击球/出界/回合结束/得分方 —— 见《数据集》文档 P017）
  - 指标定义（事件级 P/R/F1？还是最终比分正确率？）
- **现状风险**：我们目前报的是 **Recall@15px/25px**（感知层指标），
  这**不等于**判分准确率。最终对比需要**事件级真值**，现在没有。

### Q14【三分支共议】自录评测集的规格与标注格式

- **问题**：《数据集》文档建议"自行录制完整回合补充判分标签"，但未定：
  - 分辨率 / 帧率 / 机位 / 场次 / 时长
  - 标注格式（谁标？用什么工具？格式？）
- **为什么重要**：这直接决定我们要做几套球台标定、以及评测脚本怎么写。

### Q15【问组长】TT3D 的获取谁去推进

- **问题**：《数据集》文档说 TT3D **商用许可尚未确认、需要联系作者**。
- **为什么现在问**：这是**长周期行政事项**，等到要用就晚了。建议尽早并行推进。
- **顺带提醒（不是问题）**：TT3D 的 200Hz 是**真值采样率**、不代表视频帧率。
  用它验证落点必须按**时间戳重采样**，按帧号对齐会错位。

## 4. 我们要报备的（非提问，但请知悉）

我们为不阻塞开发，已按业界惯例自行拍板了 13 条决策，完整清单见
[决策与风险记录.md](决策与风险记录.md)（每条含依据、风险、回滚方式）。其中需要三家知道的：

| 项 | 我们的取值 |
|:---|:---|
| `frame_id` | 从 0 起（Q1） |
| `timestamp_s` | `frame_id / 视频实际fps`，非墙钟（Q3） |
| `side` | 物理左右，A=左（Q2） |
| 事件枚举 | `BOUNCE` / `RACKET_HIT` / `NET_TOUCH` / `OUT`（Q5） |
| 去重窗 | ±0.08s（Q7） |
| 事件级 confidence | 事件层自评，与模型原始分数解耦（Q6） |
| 多候选 | 走适配器**带外通道** `candidates_for()`，**不写进 §7.1 观测结构** |
| `OUT` 判据 | 只认"台外落点拐点"且限定在图像良态区（远端长球不捕获，交给状态机超时判据） |
| 目录布局 | `core/` + `adapters/`（本分支自定，非硬性） |

**特别说明一条**：我们曾一度把"一帧多候选"字段加进 `FrameObservation`，
后来按 §7.1 的冻结性**撤回了**，改走带外通道。理由是：§7.1 是三分支共用的冻结接口，
各分支自行加字段会让"统一观测"退化成各说各话。**如果组里确实需要"候选级融合"，
请走正式修订。**
