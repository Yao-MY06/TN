## 1. 数据流与问题

```
观测 JSONL ──► MixedEventSource ──► RefereeStateMachine
                ├─ inner: TrajectoryEventProcessor（在线推 RACKET_HIT）
                └─ pending: 外部 BOUNCE/OUT（我方 detect_bounce 预计算）
```

### 问题：击球事件晚于它造成的落台 → OWN_COURT 误判

对方轨迹层的击球检测要"看到 vx 反转后几帧"才触发，时间戳系统性滞后。game_4 片段
（470~526 s）实测滞后 0~17 ms，造成 2 次误判：

```
13.633s BOUNCE(A)      ← 上一拍，此刻 last_hitter = B
13.900s BOUNCE(B)      ← 外部事件到点立即注入；last_hitter 还是 B
                         → 状态机判 OWN_COURT「球落在击球方(B)自己半台」P1 得分 ❌
13.917s RACKET_HIT(A)  ← 真实顺序里这一拍在 ~13.88s，先于落台
```

实际是一段 10 秒的连续对拉（13.7~23.5 s），落台/击球严格交替：`BOUNCE(A) → HIT(A) →
BOUNCE(B) → HIT(B) → …`。旧版这两条 OWN_COURT 把一段对拉拆成三分判给 P1。

**物理依据**：人对弹地球的反应 ≥200 ms，"落台后 17 ms 内击球"不可能是真实先后，
只能是击球检测滞后。

## 2. 改动 #1：外部事件注入延迟（已实施）

### 实现

1. `argparse` 新增 `--bounce-delay`，**默认 0.07**（120 fps 下 9 帧）。
2. `MixedEventSource.__init__` 新增 `delay_s` 参数，存 `self.delay_s`。
3. 释放条件改为：

```python
while self.pending and self.pending[0].timestamp_s + self.delay_s <= t + 1e-9:
```

4. **时间戳钳制**（必需）：`state_machine.py:223` 会断言事件时间戳单调不减
   （`event timestamp went backwards`）。延迟注入后，落台的原时间戳可能已被更晚送达的
   击球超过，因此释放时把它的**传递时间**钳到已送达的最新时刻：

```python
if ev.timestamp_s < self.last_released_t:
    self.stats["timestamp_clamped"] += 1
    ev.timestamp_s = self.last_released_t
self.last_released_t = max(self.last_released_t, ev.timestamp_s)
```

`last_released_t` 同时要在内层事件（击球）append 后更新，否则击球不计入，钳制会漏。

### 语义边界

- 改动的是**事件交付时刻**，不是检测时刻；我方原始检测文件
  （`outputs/*_bounces.jsonl`）与 GT 评测完全不受影响。
- 实测钳制量：game_4 两处，17 ms 与 8 ms；test_2 零处。

## 3. 改动 #2：同侧击球守卫 —— 已评估，**否决，未实施**

### 原假设

test_2 `26.458s RACKET_HIT(B)` 与 `26.467s BOUNCE(B)` 同侧、间隔 9 ms，原判断是
"球还在拍上，落台是拍上球影的伪检"，因此计划丢弃这条落台。

### GT 否定了这个假设

`_data/openttgames/test_annotations/test_2_extracted/events_markup.json`：

```
26.467s bounce   ← 真实落台
26.642s net      ← 发球擦网
26.875s bounce   ← 擦网后落在对方半台
```

同侧另一处也一样：

```
18.425s bounce   ← 真实落台（我方 RACKET_HIT 也恰好在这一帧）
18.825s bounce
```

**两处都是落台真实、击球虚假。** 击球来自轨迹层对"球弹跳导致的方向反转"的误判
（18.425 s 击球与落台同帧，26.458 s 提前 9 ms）。

### 实测后果（实施后已回滚）

丢弃这两条真落台后：

| 位置 | 新产生的判罚 | GT 事实 |
|---|---|---|
| 18.900 s | `SERVE_FAULT`，P1 得分 | 发球合法（己方落台 18.425 被丢弃） |
| 26.950 s | `SERVE_FAULT`，P1 得分 | 发球擦网 → 应判 LET 重发，不是发球失误 |
| 落台总数 | test_2 32 → 30（丢 2 条真阳性） | — |

比分由 0:3 变成 2:3，但多出的 2 分**都是误判**。所以守卫方向应当反过来（丢击球），
而丢掉击球会破坏发球识别——这些"假击球"恰好是状态机识别发球的唯一信号。**结论：不改。**

### 从这里得到的教训

- 同侧 ±60 ms 的击球-落台配对确实必有一假，但**不能假设假的是落台**；
- 判断哪一方为假必须回到 GT，不能只凭物理直觉；
- 擦网（net）在两路事件层都不可得（`event_scores.net_hit` 恒 null，单目侧视已验证
  四个假设全否定），"发球擦网"的回合我们最多做到不判分，做不到判 LET。

## 5. 改动 #3：发球守卫（SERVE_FAULT 证据链检查）

### 问题

`53.250s SERVE_FAULT`（P1 得分，2:1）是误判。GT 事实：

```
52.833s bounce  己方（B）半台，发球第一跳      ← 模型这段全漏检
53.033s net     发球擦网
53.250s bounce  擦网后落在对方（A）半台        ← 真实落台，我们看对了
```

模型在 52.55~52.83 s 连续 34 帧无输出，52.833 那条是 `confidence=0.000` 的假点（霍夫圆，
y 偏 26 px）。状态机只看到"击球后球直接落在对方半台"，于是判"发球未落己方半台"→ 白送 1 分。
正确判罚应为 LET（擦网重发），至少也是不判分。

### 关键判断：这是**缺失证据**，不是**反证**

`enable_serve_fault` 的逻辑是"己方首跳没出现 → 发球失误"。但"没出现"有两种成因：
球真的没落己方半台，或者**模型没看见**。两者在输出上完全一样，靠单条落台无法区分。

### 实现

`--serve-guard-lookback`（默认 0.45 s）+ `--serve-guard-max-hole`（默认 0.08 s）。
在外部落台提交给状态机之前做一次检查：

```python
if sm.state == SERVE_IN_PROGRESS and not sm._ctx.serve_own_bounce_seen \
        and ev.side != sm._ctx.server:
    hole = longest_dropout(hit_t - lookback, ev.timestamp_s)
    if hole >= max_hole:
        # 撤下这条落台 → 状态机不会走 SERVE_FAULT，改为 SERVE_INCOMPLETE 超时收尾（不判分）
        sm._reset_rally(keep_server=True)
```

三个实现细节都是被实测逼出来的：

1. **窗口必须往前回溯**。只盯 `[击球, 落台]` 时 game_4 完全不触发——真实盲区在
   52.55~52.83 s，**整段落在击球时刻（52.85 s）之前**。原因是轨迹层那个"击球"本身就是
   假点带出来的，它不在真实击球位置上。回溯 0.45 s 才覆盖到。
2. **必须清空回合上下文**。落台被撤下后若什么都不做，下一拍的对打落台会被当成
   "发球首跳"，后面整轮判罚全部错位。
3. **盲区用轨迹层视角统计**（即低置信点已按改动 #4 屏蔽后的可见性），否则
   `conf=0.000` 的假点会把盲区"填上"，守卫失效。

### 为什么阈值取 0.08 s

| 场景 | 发球窗口内最长盲区 | 处理 |
|---|---|---|
| game_4 53.175 s（误判） | 0.442 s | 拦截 |
| test_2 0.900 s（存疑） | 0.392 s | 拦截 |
| 正常回合发球（两视频其余全部） | 0 | 不触发 |

0.08 s ≈ 120 fps 下 10 帧，远低于两个真实案例，又远高于正常发球的 0。取值不敏感。

### 自检：守卫不会无差别关闭规则

把 game_4 52.10~52.85 s 的 86 帧盲区用线性插值填满（模拟"球全程可见"的发球），
守卫**不再触发**，`53.250s SERVE_FAULT` 照常判出，比分回到 2:1。

也就是说：如果真是"发球直接过网落在对方半台"（球始终被看到），这条规则仍然生效；
守卫只在证据链有洞时降级。

## 6. 改动 #4：低置信检出过滤

### 实现

`--obs-min-conf`（默认 0.5）：置信度低于阈值的检出**只对轨迹层**改写成"本帧无检测"，
出界判据仍看原始观测。

### 阈值 0.5 的依据

game_4 全片 2655 个检出帧的置信度分布是**离散三档**，中间没有连续过渡：

| 置信度 | 帧数 | 性质 |
|---|---|---|
| 0.906 | 975 | 真球（热图峰清晰） |
| 0.749 | 1444 | 真球（常规） |
| 0.510 | 16 | 真球（临界） |
| ≤ 0.423 | 220 | 霍夫圆兜底，落点基本不在球上 |

0.5 正好切在 0.423 与 0.510 之间，是干净的分割线。

### 为什么不能作用于落台与出界

两处实测反例：

1. **出界**：球飞出后目标变小、运动模糊重，置信度**自然衰减**到 0.5 以下，而那几帧正是
   "出界"唯一的证据。全链过滤后 game_4 `45.342s OUT`（真判，1:1）直接消失。
2. **落台**：用过滤后的轨迹重跑 `events_from_observations.py`（41 条落台）再进状态机，
   `23.517s NO_RETURN`（真判，1:0）掉成死球，比分 1:1 → 0:1。

所以过滤只保留在"需要精确位置"的轨迹/击球层。

### 单独开启不能解决问题（消融）

| 配置 | game_4 比分 | 53.25 s 误判 |
|---|---|---|
| 基线 | 2:1 | 存在 |
| 仅改动 #4（`--serve-guard-max-hole 0`） | 2:1 | **仍存在** |
| 仅改动 #3（`--obs-min-conf 0`） | 1:1 | 消除 |
| 两者同开 | 1:1 | 消除 |

改动 #3 是决定性修复；改动 #4 是加固（让轨迹层不再被假点带偏，事件流少一条错误击球）。

### 适配器同步

`adapter/tracknet_adapter.py` 增加 `--min_conf`（默认 **0**，即不改变既有行为）。
设成 0.5 可以在**导出阶段**就产出一份干净观测，供纯轨迹实验使用；
但作为交付件默认值保持 0，避免下游误以为"低置信 = 漏检"而丢掉出界证据。
